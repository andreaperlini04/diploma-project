# Local - EEG IMU Capture #

## Introduction ##
This Moodle plugin captures student activity events and forwards them to an
external synchronisation backend, where they are correlated on a shared
timeline with EEG data acquired from an IDUN Guardian device.

Every event carries a millisecond timestamp on a single reference clock: the
one of the machine running the browser. Client-side events are stamped with it
directly, and server-side ones are corrected onto it. Locating an interaction
within the recorded signal therefore assumes that the browser and the EEG
acquisition run on the same machine.

## System Requirements ##
Requires Moodle 4.4 and newer versions. The plugin registers a callback on the
`core\hook\output\before_footer_html_generation` hook, introduced in Moodle 4.4;
it cannot run on earlier releases. Developed and tested on Moodle 5.2.

A reachable synchronisation backend exposing `POST /api/v1/events` is required
for events to be persisted.

## Captured events ##

Client-side, from the browser:

    navigation_clicked    input_change          question_displayed
    answer_selected       answer_changed        answer_cleared
    text_answer_entered   drag_drop_completed   video_started
    video_paused          page_loaded           clock_skew_measured

Server-side, from Moodle core events:

    user_loggedin         course_opened         activity_opened
    quiz_started          quiz_submitted        quiz_abandoned
    quiz_overdue          quiz_reviewed         lesson_started
    lesson_ended          assignment_submitted  forum_post_created
    forum_opened

Client-side events are sent directly by the browser. Server-side events are
queued to a file in `$CFG->dataroot` and relayed by the browser on the next page
the student opens, with a correction applied for the offset between the Moodle
server clock and the local clock.

Human-readable descriptions are generated by the backend: the plugin always
sends `description: null`.

## Scope and limitations ##

The tracking module is loaded on every page, for every visitor. Teachers and
administrators are tracked exactly like students; there is no consent step and
no capability to restrict the scope. Visitors who are not logged in also
produce events, carrying a null `user_id`.

The plugin implements no Privacy API provider. It has no database tables of its
own, but it does write one queue file per user under `$CFG->dataroot` and
transmits personal data to an external service, so a site serving real users
needs a provider before this is installed.

Server-side events are delivered only when the student opens another page. When
that does not happen, as is typical for `quiz_overdue`, the event is lost, and
the queue files of students who never return are not cleaned up.

## Installing manually ##

Copy the contents of this directory to

    {your/moodle/dirroot}/local/eegimucapture

In this layout `$CFG->dirroot` is the `public/` directory (see `lib/setup.php`),
so the path resolves to `public/local/eegimucapture`.

Afterwards, log in to your Moodle site as an admin and go to
_Site administration > Notifications_ to complete the installation.

Alternatively, you can run

    $ php admin/cli/upgrade.php

to complete the installation from the command line.

## Configuration ##

The backend URL defaults to

    http://localhost:8000/api/v1/events

The plugin has no settings page: the `backendurl` config value is the only way
to point it elsewhere, and it is set from the command line

    $ php admin/cli/cfg.php --component=local_eegimucapture --name=backendurl --set=https://your.backend/api/v1/events

The backend must allow the origin serving Moodle in its CORS configuration:
server-side events are relayed by the browser and are therefore subject to the
same restriction as client-side ones.

## Testing ##

The suite needs neither the synchronisation backend nor any site content:
PHPUnit and Behat build their own test sites, on the `phpu_` and `bht_` table
prefixes, independently of the main installation. Client-side events are
observed through the `sessionStorage` recorder, which is why no backend has to
be listening.

On Linux, PHPUnit requires the `en_AU.UTF-8` locale to be generated, and
`English_Australia.1252` on Windows: the value is hardcoded in
`get_locale_name()` and a missing locale aborts the run with a configuration
error before any test executes. The site itself does not need it.

29 PHPUnit tests and 6 Behat scenarios. Measured on Docker Desktop over WSL2,
the runs take about sixteen and thirty minutes respectively; building the image,
installing the dependencies and initialising the two test sites come on top and
have not been timed.

### Setting up ###

From a clean clone of the repository hosting this plugin:

    $ docker compose -f compose_dev.yaml up -d --build
    $ docker exec -w /var/www/html moodle-app composer install

`compose_dev.yaml` and not `compose.yaml`: it brings up the Selenium container
Behat needs, and the development override for OPcache.

The `composer install` is required even though the image runs one while
building. That one passes `--no-dev`, whereas PHPUnit and Behat come from
`moodle/moodle-testing`, a development dependency; and the bind mount places the
host directory over `/var/www/html`, hiding the `vendor/` built into the image.

The commands below run inside the container, from `/var/www/html`. Use
`docker exec -it` for the long ones, see the note at the end of this section.

### PHPUnit ###

    $ php admin/tool/phpunit/cli/init.php
    $ vendor/bin/phpunit --configuration public/local/eegimucapture/phpunit.xml

`--configuration` is mandatory: without it the whole Moodle core suite runs.

### Behat ###

    $ php admin/tool/behat/cli/init.php --disable-composer
    $ vendor/bin/behat --config {behat_dataroot}/behatrun/behat/behat.yml --tags '@local_eegimucapture'

`--disable-composer` skips the network update of dependencies already installed
above. The browser can be watched live at `http://localhost:7900`, served by the
Selenium container.

### Running a subset ###

A single test method, or a single test file:

    $ vendor/bin/phpunit --configuration public/local/eegimucapture/phpunit.xml --filter test_page_context_outside_a_course
    $ vendor/bin/phpunit --configuration public/local/eegimucapture/phpunit.xml public/local/eegimucapture/tests/hook_callbacks_test.php

A single Behat scenario, by naming the feature file instead of the tag:

    $ vendor/bin/behat --config {behat_dataroot}/behatrun/behat/behat.yml public/local/eegimucapture/tests/behat/student_navigation_click_is_tracked.feature

### Notes ###

Run the long commands through `docker exec -it`. Without a TTY, `Ctrl+C` does
not reach the process inside the container: it detaches the client and leaves
the command running. A surviving Behat process holds the single Selenium
session, and every later run then blocks waiting for a free slot. Terminate it
with

    $ docker exec moodle-app pkill -f "vendor/bin/behat"

Under PowerShell the Behat tag must be single-quoted: `@` is the splatting
operator, and the argument would otherwise arrive empty, running the entire
suite.
